# M07-01.1 (ampliación) — Empaquetar tu servicio como contenedor

[← Página anterior](M07-01-servicio-inferencia.md) · [Siguiente página →](M07-02-monitorizacion.md)

> Ampliación del [M07-01](M07-01-servicio-inferencia.md). Hazla cuando hayas terminado «Constrúyelo tú» (pasos 1 a 6).
>
> Lanza los comandos desde la carpeta `infra/` del repositorio.

### Objetivo

Convertir tu `m07_01_mi_servicio.py` en una **imagen de contenedor** que cualquier equipo de planta pueda descargar y arrancar con un solo comando, sin instalar Python ni copiar el modelo a mano.

### Qué está pasando

Tu servicio funciona dentro del contenedor `lab`, que tiene todas las librerías del curso y lee el modelo de la carpeta `data/`. En planta no hay carpeta `data/` ni contenedor `lab`: hay un servidor que tiene que ejecutar **exactamente** tu servicio con **exactamente** tu modelo.

Para eso se hace una **imagen**: un paquete que lleva dentro el sistema base, las librerías con su versión, tu código y el fichero del modelo. Se construye una vez (`build`), se sube a un **registro** (`push`) y cada servidor la descarga (`pull`) y la arranca.

```
 tu equipo                         registro                       planta
 ─────────                         ────────                       ──────
 Dockerfile ──▶ docker build ──▶ docker push ──▶ mi-servicio:defecto-0.1 ──▶ docker pull + run
 código + modelo + librerías                     (y su digest sha256:…)
```

### 0 — Preparar el script para arrancarlo como servicio

**Para qué:** que al arrancar el servicio no se ejecuten las pruebas del paso 5 y 6.

**Qué ocurre:** en el contenedor, el servicio lo arranca `uvicorn`, que **importa** tu fichero para encontrar `app`. Al importarlo se ejecuta todo lo que hay en él, también el `TestClient` y la lectura de `limpio.csv`, que en la imagen no existe. Metes las pruebas bajo `if __name__ == "__main__":`, que solo es cierto cuando ejecutas el fichero directamente con `python`.

Deja el final del fichero así (todas las líneas de los pasos 5 y 6, con 4 espacios delante):

```python
# --- PASO 5: llamarlo como un cliente ------------------------------------------
if __name__ == "__main__":
    cliente = TestClient(app)
    print("GET /salud ->", cliente.get("/salud").json())
    pieza = pd.read_csv("/data/limpio.csv").iloc[0]
    cuerpo = {"pieza_id": pieza["pieza_id"], **{c: float(pieza[c]) for c in ["temperatura_c", "vibracion_mm_s", "corriente_a", "presion_bar"]}}
    r = cliente.post("/predecir", json=cuerpo)
    print(f"POST /predecir -> HTTP {r.status_code}", r.json())
```

Comprueba que sigue funcionando igual que antes:

```bash
docker compose --profile lab run --rm --no-deps --entrypoint python lab -W ignore /construye/m07_01_mi_servicio.py
```

**Resultado esperado:** la misma salida que al final del paso 5.

### 1 — El Dockerfile

**Para qué:** escribir la receta de la imagen.

**Qué ocurre:** creas el fichero `infra/construye/m07_01.Dockerfile` con este contenido:

```dockerfile
# Sistema base: Debian mínimo con Python 3.12 (el mismo que usa el contenedor lab)
FROM python:3.12-slim-bookworm

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

# Solo las librerías que usa el servicio, con la versión fijada.
# scikit-learn tiene que ser la misma con la que se entrenó el modelo (M03-03).
RUN pip install fastapi==0.115.4 uvicorn==0.32.0 httpx==0.27.2 \
        pandas==2.2.3 numpy==2.1.3 scikit-learn==1.5.2 joblib==1.4.2

# Un usuario sin privilegios: el servicio no necesita ser root
RUN useradd --create-home --uid 10001 servicio

# El modelo y su versión viajan DENTRO de la imagen, en la misma ruta que espera el script
COPY data/modelo_defecto.joblib data/VERSION /data/
COPY construye/m07_01_mi_servicio.py /app/mi_servicio.py

WORKDIR /app
USER servicio
EXPOSE 8000

# Docker pregunta a /salud cada 30 s; si no contesta, marca el contenedor como unhealthy
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/salud')"

CMD ["uvicorn", "mi_servicio:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Cómo se lee:**

| Línea | Qué hace |
|-------|----------|
| `FROM` | Parte de una imagen oficial que ya tiene Python |
| `RUN pip install …` | Instala las librerías **con versión fija**: la imagen de hoy y la de dentro de un año llevan las mismas |
| `COPY data/…` | Mete el modelo en la imagen. La imagen ya no depende de ninguna carpeta del servidor |
| `USER servicio` | El proceso no corre como root (lo verás en M08) |
| `HEALTHCHECK` | Usa tu `/salud` para que Docker sepa si el servicio está vivo |
| `CMD` | Arranca `uvicorn` con `app` de `mi_servicio.py`, escuchando en el puerto 8000 |

Fíjate en el orden: lo que cambia poco (sistema, librerías) va arriba y lo que cambia a menudo (modelo, código) abajo. Docker reutiliza las capas que no han cambiado, así que al cambiar el modelo solo se rehacen las dos últimas.

### 2 — Qué entra en la imagen

**Para qué:** que `docker build` no mande al constructor 2 GB de modelos de lenguaje que no necesita.

**Qué ocurre:** el `build` se lanza desde `infra/`, y por defecto Docker empaqueta **toda** la carpeta como contexto, incluida `modelos/` (el GGUF del M05). Creas `infra/construye/m07_01.Dockerfile.dockerignore` (mismo nombre que el Dockerfile más `.dockerignore`; Docker lo usa solo para ese Dockerfile):

```text
# Fuera todo…
*
# …salvo lo que copia el Dockerfile
!construye/m07_01_mi_servicio.py
!data/modelo_defecto.joblib
!data/VERSION
```

### 3 — Construir la imagen (build)

**Para qué:** generar la imagen y ponerle un nombre que diga qué modelo lleva.

**Qué ocurre:** construyes la imagen y la etiquetas (`-t`) con la versión del fichero `VERSION`. Además le pegas la huella del modelo como **etiqueta de metadatos** (`--label`), para que un auditor pueda leerla sin arrancar el contenedor.

```bash
VERSION=$(cat data/VERSION)
HUELLA=$(sha256sum data/modelo_defecto.joblib | cut -c1-12)

docker build -f construye/m07_01.Dockerfile \
  -t mi-servicio:$VERSION \
  --label huella_modelo=$HUELLA \
  .

docker image ls mi-servicio
docker image inspect mi-servicio:$VERSION --format '{{ index .Config.Labels "huella_modelo" }}'
```

**Resultado esperado:**

```text
REPOSITORY    TAG           IMAGE ID       CREATED          SIZE
mi-servicio   defecto-0.1   …              10 seconds ago   476MB
69a897cdf955
```

**Cómo se lee:** el nombre dice la versión (`defecto-0.1`) y la etiqueta dice la huella. El punto final del comando es el contexto: la carpeta `infra/`, filtrada por el `.dockerignore`.

### 4 — Probarla antes de distribuirla

**Para qué:** comprobar que la imagen funciona sola, sin el `docker compose` del curso ni la carpeta `data/`.

**Qué ocurre:** la arrancas en el puerto 8001 (el 8000 lo ocupa el servicio `api` del lab) y le haces las mismas preguntas que en el M07-01.

```bash
docker run -d --rm --name mi-servicio -p 127.0.0.1:8001:8000 mi-servicio:$VERSION
sleep 5

curl -s http://localhost:8001/salud
curl -s -X POST http://localhost:8001/predecir \
  -H 'Content-Type: application/json' \
  -d '{"pieza_id": "DEMO1", "temperatura_c": 61.4, "vibracion_mm_s": 0.25, "corriente_a": 4.1, "presion_bar": 6.0}'

# Estado según el HEALTHCHECK (starting → healthy)
docker inspect mi-servicio --format '{{.State.Health.Status}}'

docker stop mi-servicio
```

**Resultado esperado:**

```text
{"estado":"ok","version":"defecto-0.1","huella_modelo":"69a897cdf955"}
{"pieza_id":"DEMO1","dictamen":"seguir","probabilidad":0.08,"ts":"…","version":"defecto-0.1","huella_modelo":"69a897cdf955"}
healthy
```

**Cómo se lee:** la misma versión y la misma huella que el servicio del lab: la imagen lleva dentro el mismo modelo. No hay ningún volumen montado; todo lo que necesita está en la imagen.

### 5 — Subirla a un registro (push)

**Para qué:** dejar la imagen en un sitio desde el que la puedan descargar los servidores de planta.

**Qué ocurre:** un registro es un almacén de imágenes. Aquí usamos **uno local**, en el puerto 5001, para practicar sin cuenta y sin publicar nada. El procedimiento es el mismo con un registro en internet, como **Docker Hub** o **GitHub Container Registry (GHCR)**, o con el registro corporativo de una empresa (Harbor, GitLab, Azure/AWS/Google): lo único que cambia es la dirección que va delante del nombre. Tienes las dos variantes al final del paso.

El nombre de la imagen tiene que empezar por la dirección del registro, así que primero le pones un segundo nombre (`tag`) y luego la subes.

```bash
# Registro de prácticas (solo accesible desde tu equipo)
docker run -d --rm --name registro -p 127.0.0.1:5001:5000 registry:2

docker tag mi-servicio:$VERSION localhost:5001/mi-servicio:$VERSION
docker push localhost:5001/mi-servicio:$VERSION

# Qué versiones hay en el registro
curl -s http://localhost:5001/v2/mi-servicio/tags/list
```

**Resultado esperado:**

```text
defecto-0.1: digest: sha256:f3414b24… size: 2201
{"name":"mi-servicio","tags":["defecto-0.1"]}
```

#### Variante: GitHub Container Registry (ghcr.io)

Si tienes cuenta de GitHub, puedes usar su registro con el mismo `gh` que ya usas. Primero le das al token de `gh` permiso para publicar paquetes. Después inicias sesión en Docker con ese token, que pasas por la entrada estándar para que no quede en el historial:

```bash
gh auth refresh -s write:packages                     # una vez: añade el permiso al token
gh auth token | docker login ghcr.io -u <usuario-gh> --password-stdin

docker tag  mi-servicio:$VERSION ghcr.io/<usuario-u-organizacion>/mi-servicio:$VERSION
docker push ghcr.io/<usuario-u-organizacion>/mi-servicio:$VERSION
```

La imagen aparece en la pestaña **Packages** de tu perfil o de tu organización. Al crearse es **privada**: para descargarla, otro equipo tiene que hacer `docker login ghcr.io`. Si quieres que se pueda descargar sin iniciar sesión, cambia la visibilidad en *Package settings*.

#### Variante: Docker Hub (docker.io)

Con una cuenta de [Docker Hub](https://hub.docker.com), crea un *Personal access token* en *Account settings → Personal access tokens* y úsalo como contraseña:

```bash
docker login -u <usuario-dockerhub>                   # pide el token
docker tag  mi-servicio:$VERSION <usuario-dockerhub>/mi-servicio:$VERSION
docker push <usuario-dockerhub>/mi-servicio:$VERSION
```

Docker Hub es el registro por defecto, así que su dirección no hace falta escribirla. El repositorio se crea **público** si no lo cambias en la web.

> [!WARNING]
> En un registro público, cualquiera puede descargar la imagen, y con ella **el modelo que lleva dentro**. Usa un registro público solo con modelos que puedas compartir.

En el paso 6, sustituye `localhost:5001/` por `ghcr.io/<usuario-u-organizacion>/` o por `<usuario-dockerhub>/`.

**Cómo se lee:** el `push` devuelve un **digest** (`sha256:…`): la huella de la imagen completa, igual que `huella_modelo` es la huella del modelo. La etiqueta `defecto-0.1` se puede mover a otra imagen; el digest no. Por eso en producción se despliega por digest.

### 6 — Descargarla y arrancarla en otro equipo (pull)

**Para qué:** ver lo que haría el servidor de planta.

**Qué ocurre:** borras tus copias locales, como si estuvieras en un equipo nuevo, y la arrancas desde el registro. `docker run` la descarga sola si no la tiene.

```bash
docker rmi mi-servicio:$VERSION localhost:5001/mi-servicio:$VERSION

docker run -d --rm --name mi-servicio -p 127.0.0.1:8001:8000 localhost:5001/mi-servicio:$VERSION
sleep 5
curl -s http://localhost:8001/salud

# Lo más seguro: arrancar por digest (copia el tuyo del paso 5)
# docker run -d … localhost:5001/mi-servicio@sha256:f3414b24…

docker stop mi-servicio registro
```

**Resultado esperado:**

```text
Unable to find image 'localhost:5001/mi-servicio:defecto-0.1' locally
…
{"estado":"ok","version":"defecto-0.1","huella_modelo":"69a897cdf955"}
```

**Cómo se lee:** el equipo de planta solo ha necesitado Docker y el nombre de la imagen. Ni Python, ni librerías, ni el fichero del modelo.

> [!NOTE]
> El registro de prácticas se lanzó con `--rm` y sin volumen: al pararlo se borran las imágenes que tenía. Es lo que quieres para practicar, no para producción.

## Mejora: una imagen para equipos edge ARM

Muchos equipos de borde (M06) son ARM, no x86. Con `buildx` construyes la imagen para las dos arquitecturas y la subes en un solo paso; cada equipo descarga la suya con el mismo nombre:

```bash
docker buildx create --use --name multi
docker buildx build -f construye/m07_01.Dockerfile \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/<organizacion>/mi-servicio:$VERSION \
  --label huella_modelo=$HUELLA \
  --push .
```

## Errores frecuentes

| Síntoma | Causa probable | Cómo arreglarlo |
|---------|----------------|-----------------|
| `FileNotFoundError: /data/limpio.csv` en `docker logs mi-servicio` | las pruebas del paso 5 no están bajo `if __name__ == "__main__":` | paso 0 |
| `COPY failed: … not found` | lanzaste el `build` fuera de `infra/`, o falta la excepción en el `.dockerignore` | `cd infra`; revisa las líneas `!` del paso 2 |
| `transferring context: 2.1GB` | Docker no encuentra el `.dockerignore` | tiene que llamarse igual que el Dockerfile más `.dockerignore`, en la misma carpeta |
| `InconsistentVersionWarning` de scikit-learn | la imagen tiene otra versión de scikit-learn que la del entrenamiento | fija la misma versión que en `infra/requirements.txt` |
| `port is already allocated` | el 8001 o el 5001 están ocupados | cambia el primer número de `-p` |
| `denied: requested access to the resource is denied` | no has hecho `docker login`, o el nombre no lleva tu organización | `docker login <registro>` y revisa el nombre |
| `http: server gave HTTP response to HTTPS client` | el registro no es `localhost` y no tiene TLS | usa `localhost:5001` para practicar; un registro real va con HTTPS |

## Conclusiones

- Una **imagen** congela el servicio entero: sistema, librerías con versión, código y modelo. Lo que probaste es lo que se ejecuta en planta.
- Meter el modelo **dentro** de la imagen hace que cambiar de modelo sea **construir y desplegar una imagen nueva**, no copiar ficheros a un servidor.
- La cadena de trazabilidad queda así: **dictamen → `huella_modelo` → imagen (`digest`) → registro**.

> 🔑 `build` lo hace una vez quien entrega el modelo; `push` lo publica; `pull` lo trae a cada equipo. Despliega por digest: es la única etiqueta que nadie puede mover.
